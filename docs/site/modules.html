模块、输入输出与设备分工

目标：一台普通电脑可以完成资料整理、观看、标注和剪辑；一台GPU电脑负责模型开发。两者交换有版本的文件，未来再由工作台统一调度。

1. 从视频到成片的七个环节

环节输入输出当前入口与边界
资料登记视频文件、来源/使用范围、比赛信息Asset清单、文件hash、视频参数、源时间索引packages.library.cli；训练资料目录由build_annotation_catalog.py生成。不会把下载候选当成已存在素材
人工标注已登记视频、人物/队伍、标签目录回合/触球/动作区间、标签、圈选、修订；训练数据快照Web /training。不用GPU。基础信息手填，标签可拖放，修改可回查
训练数据准备冻结快照、对应Asset清单及只读原视频可用性报告、按组划分检查、源帧采样计划及解码摘要packages.models.training_prepare。CPU可运行，不会因为检查完成就开始训练
模型训练与评测合格人工标签、独立比赛划分、预训练权重和实验配置权重、评测报告、参数/环境记录、模型卡单独GPU环境。现有环境和实验适配器可复用；细手法/步法/技战术的完整训练器和合格数据仍待开发，不能一键承诺训练成功
自动分析JobRequest、Asset、模型卡、参数JobResult、特征/候选、来源时间、进度与失败原因packages.models及scripts/models中的已登记适配器。模型缺失时明确不可用；候选不会自动成为人工标注
检索与选片人工事件/分析结果、中文查询或条件QuerySpec、候选及依据、选片列表、Timeline当前由工作台API与页面承载。规则检索可走CPU；LLM或视频向量模型为可选环境，不是独立部署完成的检索服务
剪辑与导出Timeline、可制作用途的Asset、编码配置MP4、源片映射、质量报告python -m packages.render run或工作台。CPU编码可用；NVENC为可选，不等于需要训练级GPU

训练素材只走训练线；有制作权限的素材走检索、剪辑线。训练得到的模型可以分析制作素材，但不能因此把训练原片变成制作素材。

2. 五个源码包与一个完整包

源码按既有边界打包，不拆成互相重复的仓库：

源码包独立开发的内容携带的共享依赖设备
core数据合同、路径/容量/任务等公共运行组件标准库、轻量合同依赖普通CPU
library来源、下载/登记、探测、清单与训练目录必需core和配置普通CPU；探测需FFmpeg/ffprobe
workbench项目、播放、标注、检索、剪辑控制、任务管理core、页面资源、词表及默认配置普通CPU；播放靠浏览器，编码由render处理
models数据准备、模型适配器、训练/评测开发core、词表、模型配置与环境说明数据准备用CPU；模型运行/训练按独立GPU配置
render逻辑范围、时间线、编码、质量检查core、渲染配置CPU+FFmpeg；硬件编码可选
complete集成开发与最终业务流程上述源码与集成文档按任务选择环境，解压完整包不等于安装全部模型

每包附版本/hash清单和继续开发说明。完整Git历史包用于恢复分支和提交记录；源码ZIP用于快速部署或只开发某个模块。模块ZIP中的共享依赖是该版本的只读基线，跨模块协议修改应回到完整仓库统一提交，避免设备各改一份不兼容合同。

Python环境与源码包是两件事。源码含模型代码不代表CPU电脑需要安装CUDA；按所选部署profile安装依赖即可。完整包也不包含视频、数据库、模型权重、缓存或旧虚拟环境。

3. 按设备选择环境

设备/用途必要环境不需要安装说明
标注笔记本/台式机Python、工作台venv、现代浏览器Torch、CUDA、Conda训练环境视频编码格式不被浏览器支持时需要受控代理，FFmpeg按需配置
剪辑电脑轻量render环境、FFmpeg/ffprobe、可用字体训练框架CPU能导出；分辨率、长度和编码设置决定耗时，不能按显卡型号保证速度
数据准备设备CPU准备环境、原片及快照CUDA、LLM、重型视觉框架检查数据并解码采样帧，正式训练条件不足会列缺项
训练/批量分析设备WSL Ubuntu、独立模型环境、适配的NVIDIA驱动与GPU工作台生产数据库本项目训练以WSL Ubuntu为验收目标；其他Linux设备需做对应验收
较大模型设备单独VL等环境、匹配的权重将冲突版本装入同一环境5090是已有实验设备；换GPU须重新测算子、显存、速度和模型效果

内存、显存、磁盘峰值需要按模型和视频窗口实测。环境脚本能检查前提，不代表在所有GPU上训练性能已验证。

4. 模块之间怎样交接

文件或对象谁生成 → 谁读取必须保留
Asset manifestlibrary → 工作台/模型/renderasset_id、相对路径、hash、时长/源时间、来源和用途
TrainingSnapshot标注工作台 → 数据准备/训练快照hash、标签版本、标注修订、人物/角色、区域、审核与比赛组
JobRequest / JobResult工作台/实验runner ↔ 模型/renderjob/attempt、输入身份、参数、成功/失败/阻塞、产物hash
Event / Candidate人工或分析 → 检索/审核时间、人物、标签、证据、未确认状态，不把未知转阴性
Timeline工作台 → render片段顺序、原片边界、速度/标题/画幅、审核与用途
模型卡与评测报告模型开发 → 工作台配置权重hash、环境、支持范围、真实效果、许可证

文件路径按各设备的storage root解析，不能在合同里写死某人的用户名。模型和渲染不得直接写工作台SQLite。现有跨设备方式是受控的文件交接，不包含已实现的远程作业调度或自动双向数据库合并。

5. 将来怎样组成完整流程

  1. 在资料设备生成并校验资产清单，把必要原片按相对路径同步到目标设备。
  2. 在标注设备完成标注、复核、比赛分组，导出一个冻结快照。
  3. 在数据准备/训练设备校验快照与源片hash；先取得可读报告，再决定补标或启动合格实验。
  4. 模型产物和评测通过后，登记模型卡和受控启动命令，再由工作台选择明确版本运行。当前Windows→WSL自动执行桥仍限制D:/video对应路径；换盘后的独立模型CLI可用，接回网页调度还需改造并验收该桥，不能只复制模型卡。
  5. 对制作素材分析、检索并人工选片；把Timeline和原片引用交给render。
  6. 把MP4、源映射和质量报告回交工作台。各步失败有自己的结果文件，不通过伪进度跳过。

独立模块先以CLI/JSON完成交接；有跨设备在线协作需求时，再在这些合同外增加鉴权和远程执行器。当前不开放公网端口，也不让多台电脑同时写同一个SQLite文件。

部署与迁移操作见迁移指南，当前实测范围见本轮验证。
