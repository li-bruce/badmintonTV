# 分阶段目标与验收结果

更新：2026-09-29。阶段沿用 [原计划](../PROJECT_PLAN_SIMPLE.md) 的 0–5 与 V2，四个模块共同完成阶段，不把四个任务当成四个顺序阶段。

这是产品验收用例表，采用单元测试的“给定条件 → 执行动作 → 断言结果”写法；不是新增自动化测试执行记录。本次依据已保存证据整理，没有重跑训练、浏览器或回归。证据基线：运行源码 `a851dcb`、集成交付记录 `1477b34`。

## 判定规则

| 结果 | 含义 | 计为达标 |
|---|---|---|
| PASS | 在写明的数据、环境和范围内，实际结果满足全部断言 | 是 |
| FAIL | 已执行，但实测结果不满足断言 | 否 |
| BLOCKED | 缺少明确前置条件，暂不能完成验证；必须写解除条件 | 否 |
| NOT_RUN | 尚未实现或未验证；必须写下一步 | 否 |

“已实现”“experimental”“运行成功”和测试 SKIP 都不能直接计为产品 PASS。一个用例有多条断言时，必须全部满足。下列阶段内用例均为该阶段必需项；全部 PASS 才将阶段标为达标，否则为未达标，并保留已经通过的项。前置阶段未完成时，允许按原计划继续不依赖它的工程工作。

PASS 只适用于证据注明的范围：单元夹具、真实小样、完整比赛、人类真值分别记录；个人录像、转播、单打、双打的结果不能互相替代。证据失效或代码变化影响断言时，先回到 NOT_RUN，再验证，不能沿用旧 PASS。

## 后续每阶段的更新格式

每次开发前明确本轮要关闭的用例 ID 和断言，完成后更新“实际结果、状态、证据、未达标原因/下一步”。先登记新目标再实现；不得为了通过而悄悄降低原门槛。变更门槛时保留旧版本、原因和日期。

四个模块在自己的 `docs/status/<module>.md` 引用这些 ID，记录模块证据；主任务维护本表的阶段总状态。新增子目标可用 `S2-03a` 等稳定编号，调整计数时保留历史记录；不另建含义相同却状态冲突的清单。

```text
用例 ID / 责任模块：
目标要求（Given / When / Then）：
输入数据、环境、代码/模型版本：
验证命令或人工操作：
预期结果：
实际结果（数量、错误、跳过和适用范围）：
当前状态：PASS / FAIL / BLOCKED / NOT_RUN
证据（报告/任务 ID/产物路径，注明验证日期）：
未达标原因与下一步（BLOCKED 须写解除条件）：
```
